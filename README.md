## 1. Project Overview

CloudForge is a computer networking project that implements and evaluates a software-based HTTP load balancer in a controlled Linux networking environment.

The system distributes incoming HTTP requests across two application servers using different load-balancing strategies. It monitors backend health, excludes unavailable servers, reinstates recovered servers, and handles eligible request failures.

The project uses Linux network namespaces, virtual Ethernet interfaces, static routing, two software routers, FastAPI application servers, and a shared PostgreSQL database.

The primary objective is to study how different load-balancing strategies behave under controlled network conditions, including delay, packet loss, bandwidth limitations, and backend failures.

## 2. Objectives

The main objectives are to:

- Implement HTTP request forwarding through a central gateway.
- Implement Round Robin (RR) load balancing.
- Implement Least Outstanding Requests (LOR) load balancing.
- Monitor backend availability through periodic readiness checks.
- Exclude unhealthy backends and reinstate recovered servers.
- Implement bounded retry for eligible read requests.
- Prevent unsafe automatic retries of write operations.
- Measure performance under different network conditions.
- Analyze packet-level communication using Wireshark.
- Compare load-balancing strategies using experimental results.

### 3.3 Linux Network Namespaces

The implemented network namespace layout is:

| Namespace | Purpose |
|---|---|
| `cf-client` | Client |
| `cf-gateway` | HTTP gateway and load balancer |
| `cf-r1` | First software router |
| `cf-r2` | Second software router |
| `cf-app-a` | Application server A |
| `cf-app-b` | Application server B |

PostgreSQL runs in the Ubuntu host namespace rather than in a separate network namespace. The host is attached to the database subnet through the `br-cf-db` Linux bridge, using `10.10.4.10:5432`.

### 3.4 Communication Flow

The principal application request follows this path:

1. The client sends an HTTP request to the gateway at `10.10.1.20:8000`.
2. The gateway selects a healthy backend using the configured load-balancing policy.
3. Traffic travels through Router 1 and Router 2.
4. The selected backend processes the request.
5. If required, the backend communicates with PostgreSQL at `10.10.4.10:5432`.
6. The backend returns its response through the network.
7. The gateway forwards the response to the client.

Health probes are generated by the gateway and sent to the backend readiness endpoints.

## 5. Load-Balancing Functionality

The gateway implements the following functionality.

### 5.1 HTTP Request Forwarding

The gateway accepts supported HTTP methods, forwards requests asynchronously using HTTPX, and returns the backend response.

Request IDs are propagated across the gateway and backend, and hop-by-hop headers are filtered.

The gateway exposes `/gateway/status` for backend health and outstanding-request visibility.

### 5.2 Round Robin

Requests are distributed sequentially across available healthy backends. The selection cursor is updated under an asynchronous lock.

### 5.3 Least Outstanding Requests

The gateway selects the healthy backend with the lowest number of currently outstanding requests.

When multiple healthy backends have equal outstanding counts, a rotating tie-breaker provides fair selection. Backend selection and outstanding-counter updates are performed under an asynchronous lock. Counters are released after forwarding attempts complete.

### 5.4 Backend Health Management

The gateway periodically checks each backend's `/health/ready` endpoint.

Current health-monitor configuration:

- Health-check interval: 2 seconds.
- Health-check timeout: 1 second.
- Failure threshold: 2 consecutive failed probes.
- Recovery threshold: 2 consecutive successful probes.

Unhealthy backends are excluded from selection. Recovered backends become eligible again after the recovery threshold is satisfied.

### 5.5 Bounded Failure Handling

The gateway implements bounded retry with a maximum of two attempts and one shared 3-second forwarding deadline.

- Only GET and HEAD requests are eligible for retry.
- Retry is permitted only for connection-establishment failures (`httpx.ConnectError` and `httpx.ConnectTimeout`).
- The retry selects another healthy backend, excluding the backend that failed to connect.
- HTTP error responses, read timeouts, and other request errors are not retried.
- POST, PUT, PATCH, DELETE, and OPTIONS requests are not retried.

Write requests are not automatically retried because a failed response does not establish whether the database transaction committed.

The retry behavior has passed seven isolated tests using HTTPX mock transports. These tests validate retry behavior but are not part of the formal performance evaluation.

### 5.6 Monitoring and Visibility

The gateway currently provides:

- Backend health status through `/gateway/status`.
- Consecutive health-check success and failure counts.
- Last health-check status.
- Outstanding request counts.
- Request IDs and backend identity response headers.
- Gateway request timing.
- Backend connection-failure and forwarding logs.
- Backend health and recovery logs.

Formal performance metrics will be collected during the planned evaluation.

## 6. Experimental Methodology

The project compares Round Robin and Least Outstanding Requests under controlled network conditions.

Every measured run uses:

- 10 seconds of warm-up.
- 60 seconds of measurement.

The workload, backend capacity, connection reuse, dataset, and concurrency should remain consistent when comparing policies.

#### Workload Generator Configuration

The workload is generated by `scripts/workload.py` using a fixed-concurrency, closed-loop request model.

The selected calibration configuration for formal evaluation is:

- 5 concurrent worker threads.
- One persistent HTTP client connection per worker.
- GET requests to the gateway's `/users/` endpoint.
- A 5-second request timeout.
- A 10-second warm-up followed by a 60-second measurement period.

The five-worker configuration was selected from preliminary RR and LOR calibration runs. It is held constant across comparable formal policy experiments. Calibration results are separate from the approved 63 measured runs.

### 6.1 Planned Experiments

| Experiment | Conditions | Policies | Repetitions | Runs |
|---|---|---|---:|---:|
| Added round-trip delay | 20, 100, 200 ms | RR and LOR | 3 | 18 |
| Packet loss | 0%, 2%, 5% | RR and LOR | 3 | 18 |
| Bandwidth | 100, 20, 5 Mbit/s | RR and LOR | 3 | 18 |
| Backend failure and recovery | Three delay conditions | Dynamic policy | 3 | 9 |
| **Total** | | | | **63** |

**Approved formal experiment count: 63 measured runs.**

Each measured run uses a 10-second warm-up followed by a 60-second measurement period. Results will be summarized using the mean and standard deviation.

Calibration observations are not counted as formal measured runs.

#### Calibration Methodology

- **Delay:** Applied on the R1-to-R2 transit egress interface. The configured one-way delay therefore produces approximately the corresponding added RTT for a round-trip ping.
- **Packet loss:** Calibrated on the R1-to-R2 egress direction.
- **Bandwidth:** Shaping applied to both R1-to-R2 and R2-to-R1 transit interfaces.

Formal experiment records must preserve these directions and configurations consistently.

### 6.2 Evaluation Metrics

The following metrics will be collected:

- Successful requests per second.
- Client-observed p50 latency for successful HTTP 2xx requests.
- Client-observed p95 latency for successful HTTP 2xx requests.
- HTTP error rate.
- Supplementary all-attempt latency statistics (mean, p50, and p95), including failed requests and timeouts.
- Backend request distribution.
- Backend failure detection time.
- Backend recovery time.
- Actual round-trip time.
- TCP retransmissions.

Results will be presented per run, along with the mean and standard deviation.

No performance advantage will be assumed before experimental evaluation.

## 14. Limitations and Scope

CloudForge is a controlled academic networking laboratory, not a production-grade cloud load-balancing platform.

The project does not aim to implement:

- High availability for the gateway itself.
- High availability for PostgreSQL.
- TLS termination.
- Automatic cloud autoscaling.
- Kubernetes deployment.
- Production-grade distributed monitoring.
- Automatic database transaction recovery.

The gateway and shared PostgreSQL database remain potential single points of failure.

## 15. Conclusion

CloudForge provides a practical environment for implementing and evaluating software-based HTTP load balancing using real Linux networking components.

By combining multiple backend servers, health monitoring, dynamic request distribution, controlled network impairments, and packet-level analysis, the project aims to demonstrate how network conditions and backend availability affect service performance.

The final evaluation will compare the implemented load-balancing policies using repeatable experiments and measurable performance metrics.
