## 1. Project Overview

CloudForge is a computer networking project that implements and evaluates a software-based HTTP load balancer in a controlled Linux networking environment.

The system distributes incoming HTTP requests across two application servers using Round Robin (RR) and Least Outstanding Requests (LOR). It monitors backend health, excludes unavailable servers, reinstates recovered servers, and provides bounded retry for eligible read requests.

The project uses Linux network namespaces, virtual Ethernet interfaces, Linux bridges, static routing, two software routers, FastAPI application servers, and a shared PostgreSQL database.

The primary objective is to investigate how load-balancing strategies behave under controlled network conditions, including delay, packet loss, bandwidth limitations, and backend failures.

The project also examines the communication paths and network behavior through packet captures and performance measurements.

## 2. Objectives

The main objectives are to:

- Implement HTTP request forwarding through a central gateway.
- Implement Round Robin (RR) load balancing.
- Implement Least Outstanding Requests (LOR) load balancing.
- Provide fair backend selection when outstanding-request counts are equal.
- Monitor backend availability through periodic readiness checks.
- Exclude unhealthy backends and reinstate recovered servers.
- Implement bounded retry for eligible read requests.
- Prevent unsafe automatic retries of write operations.
- Construct a routed multi-subnet environment using Linux networking.
- Evaluate performance under different network conditions.
- Capture and analyze packet-level communication using Wireshark.
- Compare load-balancing strategies using repeatable experiments and statistical results.

### 3.5 Communication Flow

The principal application request follows this path:

1. The client sends an HTTP request to the gateway at `10.10.1.20:8000`.
2. The gateway selects a healthy backend using the configured load-balancing policy.
3. Traffic travels through Router 1 and Router 2.
4. The selected backend processes the request.
5. If required, the backend communicates with PostgreSQL at `10.10.4.10:5432`.
6. The backend returns its response through the network.
7. The gateway forwards the response to the client.

Health probes are generated by the gateway and sent to the backend readiness endpoints.

The two application backends use the same PostgreSQL database.

## 5. Load-Balancing Functionality

The gateway implements HTTP forwarding, multiple backend-selection policies, health monitoring, bounded failure handling, and operational visibility.

### 5.1 HTTP Request Forwarding

The gateway accepts supported HTTP methods, forwards requests asynchronously using HTTPX, and returns the backend response.

Request IDs are propagated across the gateway and backend, and hop-by-hop headers are filtered.

The gateway exposes `/gateway/status` for backend health and outstanding-request visibility.

### 5.2 Round Robin

Requests are distributed sequentially across available healthy backends.

The selection cursor is updated under an asynchronous lock to maintain consistent selection when concurrent requests arrive.

### 5.3 Least Outstanding Requests

The gateway selects the healthy backend with the lowest number of currently outstanding requests.

When multiple healthy backends have equal outstanding counts, a rotating tie-breaker provides fair selection.

Backend selection and outstanding-counter updates are performed under an asynchronous lock. Counters are released after forwarding attempts complete.

LOR was tested using concurrent requests and a controlled asymmetric backend-processing test.

### 5.4 Backend Health Management

The gateway periodically checks each backend's `/health/ready` endpoint.

Current health-monitor configuration:

- Health-check interval: 2 seconds.
- Health-check timeout: 1 second.
- Failure threshold: 2 consecutive failed probes.
- Recovery threshold: 2 consecutive successful probes.

Unhealthy backends are excluded from selection. Recovered backends become eligible again after the recovery threshold is satisfied.

The health endpoint also checks database availability, so a backend that cannot access the database does not report readiness.

### 5.5 Bounded Failure Handling

The gateway implements bounded retry with a maximum of two attempts and one shared 3-second forwarding deadline.

- Only GET and HEAD requests are eligible for retry.
- Retry is permitted only for connection-establishment failures (`httpx.ConnectError` and `httpx.ConnectTimeout`).
- The retry selects another healthy backend, excluding the backend that failed to connect.
- HTTP error responses, read timeouts, and other request errors are not retried.
- POST, PUT, PATCH, DELETE, and OPTIONS requests are not retried.

Write requests are not automatically retried because a failed response does not establish whether the database transaction committed.

Verification included:

- Seven isolated tests using HTTPX mock transports.
- A live GET test confirming retry to an alternate backend after a connection failure.
- A live POST test confirming that a write request is not retried.
- A test with both backends unavailable, confirming bounded attempts and failure handling.

The live verification results are saved in:

`results/evidence/bounded-retry-verification.log`

## 6. Experimental Methodology

The project compares Round Robin and Least Outstanding Requests under controlled network conditions.

### 6.1 Workload Generator Configuration

The workload is generated by `scripts/workload.py` using a fixed-concurrency, closed-loop request model.

The formal evaluation configuration is:

- 5 concurrent worker threads.
- One persistent HTTP client connection per worker.
- GET requests to the gateway's `/users/` endpoint.
- A 5-second request timeout.
- A 10-second warm-up period.
- A 60-second measurement period.

The five-worker configuration was selected from preliminary RR and LOR calibration runs.

The workload configuration was kept constant across comparable formal policy experiments.

Calibration observations are separate from the formal measured runs.

### 6.2 Formal Experiments

A total of **63 formal measured runs** were completed.

| Experiment | Conditions | Policies | Repetitions | Runs |
|---|---|---|---:|---:|
| Added round-trip delay | 20, 100, 200 ms | RR and LOR | 3 | 18 |
| Packet loss | 0%, 2%, 5% | RR and LOR | 3 | 18 |
| Bandwidth | 100, 20, 5 Mbit/s | RR and LOR | 3 | 18 |
| Backend failure and recovery | 20, 100, 200 ms delay | LOR | 3 | 9 |
| **Total** | | | | **63** |

Each formal performance condition was repeated three times.

The failure/recovery experiments used the LOR policy and three repetitions at each delay condition.

Each run used a 10-second warm-up followed by a 60-second measurement period.

### 6.3 Network Impairment Configuration

Network impairments were applied using Linux traffic control.

| Experiment | Configuration | Direction |
|---|---|---|
| Delay | 20, 100, 200 ms | R1 transit egress |
| Packet loss | 0%, 2%, 5% | R1 transit egress |
| Bandwidth | 100, 20, 5 Mbit/s | Both transit directions |

The delay was applied on the R1-to-R2 transit egress interface. The configured one-way delay therefore produces approximately the corresponding added RTT for a round-trip ping.

Packet loss was calibrated on the R1-to-R2 egress direction.

Bandwidth shaping was applied to both R1-to-R2 and R2-to-R1 transit interfaces.

### 6.4 Evaluation Metrics

The workload and analysis scripts collect and calculate:

- Successful requests per second.
- Successful request count.
- Failed request count.
- Client-observed mean latency.
- Client-observed p50 latency.
- Client-observed p95 latency.
- HTTP error rate.
- Backend request distribution.
- Supplementary all-attempt latency statistics, including failed requests and timeouts.

Latency percentiles for successful requests are calculated using successful HTTP 2xx responses.

Results are summarized using the mean and sample standard deviation across three repetitions.

Failure/recovery experiments additionally record successful throughput, latency, error rate, failed request counts, and HTTP status distribution.

Backend unhealthy and recovery transitions were verified through gateway logs and status checks. Exact failure-detection and recovery durations were not separately instrumented.

Actual RTT was measured during network impairment calibration. TCP retransmission statistics were not included in the formal performance summary.

### 6.8 Interpretation and Experimental Limitations

The results show that the relative performance of RR and LOR depends on the network condition.

Observed results include:

- At 20 ms and 100 ms delay, LOR achieved higher mean throughput and lower mean latency than RR.
- At 200 ms delay, the two policies produced similar results.
- Under baseline packet-loss conditions, RR and LOR had nearly identical performance.
- At 2% packet loss, RR achieved higher mean throughput in the observed runs.
- At 5% packet loss, LOR achieved higher mean throughput and lower mean latency.
- At 20 Mbit/s bandwidth, both policies produced nearly identical results.
- At 100 Mbit/s, RR had higher mean throughput but greater run-to-run variability.
- At 5 Mbit/s, LOR achieved higher mean throughput and lower mean latency in the observed runs.

These observations should be interpreted within the scope of the experimental workload.

The workload uses small HTTP GET requests and does not necessarily saturate the configured network bandwidth. Therefore, the results describe application performance under the configured traffic conditions rather than the maximum throughput capacity of each bandwidth setting.

Each condition contains three repetitions. Variation between runs is retained in the reported statistics rather than removing individual results without an independently justified reason.

## 14. Limitations and Scope

CloudForge is a controlled academic networking laboratory, not a production-grade cloud load-balancing platform.

The project does not aim to implement:

- High availability for the gateway itself.
- High availability for PostgreSQL.
- TLS termination.
- Automatic cloud autoscaling.
- Kubernetes deployment.
- Production-grade distributed monitoring.
- Automatic database transaction recovery.

The gateway and shared PostgreSQL database remain potential single points of failure.

The formal workload uses a fixed-concurrency, closed-loop model and small HTTP GET requests. Consequently, the observed results should not be interpreted as universal load-balancer performance or as maximum network throughput.

The formal evaluation uses three repetitions per condition. Statistical conclusions should therefore be interpreted within the scope of the tested environment and workload.

The exact duration of backend failure detection and recovery was not separately instrumented, although unhealthy and recovered state transitions were verified.

The completed evaluation contains 63 formal runs covering delay, packet loss, bandwidth limitations, and backend failure/recovery. The resulting data was validated and statistically summarized. The experimental results demonstrate how network conditions influence request throughput and latency, and how backend health management allows the gateway to continue serving traffic when one application server becomes unavailable.
